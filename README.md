# redevelopment-control

Модуль для демонстрации алгоритма контроля перепланировок. Принимает растровые планы квартир (png, jpg, webp, tif) и отдаёт JSON с рамками:

- `changes`: сравнивает план «до» и план «после», находит четыре типа изменений;
- `entities`: разбирает один план на внешние стены, перегородки, окна, двери и сантехнику.

> **Важно.** Модели обучены только на синтетических планах (датасет «Периметр» v4 и 15 размеченных планов из него). На реальных планах БТИ качество не проверено. Для демонстрации используйте примеры из `examples/` или синтетику.

## Установка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python check.py        # дымовая проверка, должна напечатать две строки OK
```

Веса уже лежат в `redevelopment_control/weights/` (две модели по 27 МБ, fp16). Интернет при работе не нужен. Работает на CPU, Apple MPS и CUDA (выбирается автоматически).

## Как пользоваться

### 1. Из командной строки

```bash
python -m redevelopment_control changes examples/changed_before.png examples/changed_after.png --overlay out.png
python -m redevelopment_control entities examples/changed_before.png --out entities.json --overlay entities.png
```

### 2. Из Python

```python
from redevelopment_control import detect_changes, parse_entities, draw

res = detect_changes("before.png", "after.png")   # путь, bytes или numpy-массив
for c in res["changes"]:
    print(c["label_ru"], c["bbox"], c["score"])

ent = parse_entities("plan.png")
```

### 3. HTTP-сервис для фронта

```bash
uvicorn redevelopment_control.server:app --port 8000
```

| Метод и путь | Тело (multipart/form-data) | Ответ |
|---|---|---|
| `GET /health` | нет | `{"ok": true}` |
| `POST /changes?mode=cnn` | файлы `before`, `after` | JSON как в `detect_changes` (по умолчанию, локально) |
| `POST /changes?mode=verify` | то же | CNN нашла кандидатов, Claude подтвердил или отбросил (нужен ключ API) |
| `POST /changes?mode=vlm` | то же | изменения ищет только Claude (нужен ключ API) |
| `POST /entities` | файл `plan` | JSON как в `parse_entities` |

CORS открыт для любого источника (удобно для демо; для продакшена ограничьте `allow_origins` в `redevelopment_control/server.py`). Сервер проверен: `/health`, `/changes`, `/entities`, ошибка 400 на битом файле и CORS работают.

```bash
curl -F before=@examples/changed_before.png -F after=@examples/changed_after.png localhost:8000/changes
```

## Модели Claude через API

Кроме локальных сетей в модуле есть два режима с моделями Claude. Им нужен пакет `anthropic` (есть в `requirements.txt`) и ключ: переменная `ANTHROPIC_API_KEY` или вход через `ant auth login`. Каждый запрос платный, по замерам исследования около 35 тыс. токенов на пару.

```python
from redevelopment_control import detect_changes, verify_changes, detect_changes_vlm

res = detect_changes("до.png", "после.png")
res = verify_changes("до.png", "после.png", res, model="claude-sonnet-5-5")   # гибрид: сеть находит, Claude проверяет
res = detect_changes_vlm("до.png", "после.png", model="claude-opus-5-5")     # только Claude
```

В командной строке: `python -m redevelopment_control changes до.png после.png --verify` или `--vlm`, модель задаётся `--model`.

| Модель | Идентификатор | Результат в исследовании (16 тестовых пар, F1 с классом) |
|---|---|---|
| Claude Fable 5.1 | `claude-fable-5-1` | 0,80; находит все изменения, 25% ложных тревог |
| Claude Opus 5.5 | `claude-opus-5-5` | 0,76; находит все изменения, 25% ложных тревог |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` (по умолчанию) | 0,67; 12% ложных тревог |
| Гибрид: классика, затем проверка Sonnet | `verify_changes` | 0,71; ложных тревог нет, но часть изменений пропущена детектором |

Что учитывать:
- В режиме `verify` в исследовании кандидатов давала классика, здесь их даёт наша сеть. Именно такая связка отдельно не измерялась.
- Режимы с Claude в `check.py` проверены только на подставном клиенте (разбор ответа и пересчёт координат). Реальные вызовы API в этом репозитории не тестировались.
- Рамки у `vlm` приблизительные: модели хуже локализуют, чем сеть. Для точных рамок используйте `cnn` или `verify`.
- При ошибке API (нет ключа, лимит, отказ модели) HTTP-сервер отвечает 502 с текстом ошибки.

## Формат ответа

В ответах режимов Claude у изменений есть поле `verified_by` (имя модели), у `verify` ещё `detector_class` (класс, который дала сеть).
Координаты рамок `bbox = [x0, y0, x1, y1]` в пикселях.
Для `changes` это кадр изображения **«после»**, для `entities` кадр входного плана.
Начало координат в левом верхнем углу, `image_size = [ширина, высота]`.

`changes`:

```json
{
  "image_size": [1100, 830],
  "aligned": true,
  "has_changes": true,
  "changes": [
    {"class_id": 3, "class": "plumbing_moved", "label_ru": "перенос сантехники",
     "bbox": [683.2, 319.9, 769.1, 386.9], "score": 0.962}
  ]
}
```

| `class_id` | `class` | Значение |
|---|---|---|
| 1 | `removed_partition` | демонтаж перегородки |
| 2 | `added_partition` | новая перегородка |
| 3 | `plumbing_moved` | перенос сантехники |
| 4 | `doorway_moved` | перенос проёма |

`aligned: false` означает, что выравнивание планов не сошлось, и результату доверять нельзя. `score` от 0 до 1.

`entities`: `{"image_size": [...], "entities": [{"class": "window", "label_ru": "окно", "bbox": [...], "score": 0.93}]}`.
Классы: `outer_wall`, `partition`, `window`, `door`, `sanitary`.

Готовые примеры выходов лежат в `examples/`: `changes_expected.json`, `entities_expected.json` и картинки с рамками `*_overlay.png`.

## Что модуль умеет и чего нет

Цифры получены на синтетике и показывают только «выучен ли генератор датасета».

| Модель | Проверка | Результат |
|---|---|---|
| Поиск изменений | 16 тестовых пар (другие семейства планов, чем при обучении) | находит все изменения с верным классом, ложных тревог нет |
| Разбор сущностей | 5-кратная кросс-валидация по семействам, 15 планов | окна, двери, сантехника: F1 0,97–1,00; перегородки 0,97; внешние стены 0,51 |

Известные ограничения:

- **Реальные планы не проверялись.** Ждите заметной просадки на сканах с другим стилем чертежа.
- **Внешние стены** модель разбора сущностей режет на куски и часть принимает за перегородки. Для демонстрации лучше не опираться на класс `outer_wall`.
- **Одно изменение может вернуться несколькими рамками** (длинная перегородка делится на два куска). Если нужна одна рамка на событие, объедините пересекающиеся рамки одного класса на стороне фронта.
- **Размер входа:** проверялось на ширине от 360 до 1450 px. Планы на фото с сильной перспективой не тестировались.
- **Порог:** `detect_changes(thr=0.7)` и `parse_entities(thr=0.5)` подобраны на синтетике. Выше порог значит меньше ложных тревог, но больше пропусков.
- Классы изменений ограничены четырьмя выше: смещение стены, окна или лоджии модуль не распознаёт.

## Откуда веса

Обучающий код и эксперименты лежат в исследовательском репозитории (`Control_of_changes_redevelopments/bench`): `cnn.py` (поиск изменений), `ent_unet_lib.py` и `train_entity_final.py` (сущности). Здесь только инференс. Архитектура у обеих моделей одинаковая: ResNet18-энкодер с UNet-декодером.

Как устроен вход поиска изменений: старый план подгоняется под новый (ECC-гомография), затем три канала 512×384: новый, старый после подгонки и модуль их разницы. У разбора сущностей на входе один серый план шириной 1100 px.
